# Host CLI commands: fingerprint verification and the traffic report

Status: ready-for-agent
Blocked by: 72, 70
Source: https://github.com/rawinan-soma/dds-sharing/issues/76 (migrated 2026-09-21)

## What to build

The privileged operations that live on the Docker host rather than on any web surface. Shell access is the bar, deliberately — these are the acts nobody should be able to perform through a browser.

> Redaction was removed from this ticket on 2026-09-14 (ADR 0019); there is no Redaction anywhere. Removing what already exists of it is #88.

**Fingerprint verification** — takes a file, an Extract archive or a bare CSV, whichever arrived, and reports which Request it came from, or reports no match. **A procedure performed by hand is how a wrong answer gets made under pressure**, so this is a command rather than a written procedure.

> ⚠️ **The command prints the asymmetry, so nobody has to remember it: a match is strong evidence; a mismatch is nearly none.** This audience opens CSVs in Excel, and a file opened and re-saved will not match although the data is unchanged. Without that line, a mismatch reads as *"this did not come from us"* — the wrong answer to the only question the checksum exists for.

It must also print that **the fingerprint attests content, never provenance**: two Requests asking the same question of the same data release identical bytes, and every empty Extract shares one, so **a match narrows to a set of Requests, never to one.**

**The upstream traffic report** — counts upstream calls over a date range, **split by Probe and fetch**. DDC issues one bearer token for the whole service and the failure mode is DDC noticing and revoking us, which no retry recovers from, so *"how much traffic are you sending?"* must be answerable. The `code_fetched` events cover running jobs; `probe_performed` covers submits **including those that were rejected or expired**; `probe_failed` covers the calls an abandoned Probe spent before giving up — traffic spent either way, and the retries make it more than a successful Probe's, not less.

**Not a dashboard and not an endpoint.** This question gets asked by a human a handful of times a year, and a dashboard nobody opens is a cost with no reader.

**Reviewer password reset and TOTP re-enrolment** also live here, on the same route, for the same reason: there is no self-service email reset path, ever, because that would let the Requester's unverified-email world reach the privileged surface. Like every host command, they do not record who ran them (ADR 0020).

## Acceptance criteria

- [ ] A fingerprint verification command accepts either an archive or a bare CSV and reports the matching Request or no match
- [ ] The command prints the match/mismatch asymmetry and the content-not-provenance caveat on every run, not only on a mismatch
- [ ] An upstream traffic report command counts calls over a date range, split by Probe and fetch, and includes rejected and expired Requests and abandoned Probes
- [ ] The traffic report is a CLI command with no HTTP endpoint and no dashboard
- [ ] Password reset and TOTP re-enrolment are CLI-only, with no email-based path anywhere in the application
- [ ] No host command takes, reads or records an operator name
